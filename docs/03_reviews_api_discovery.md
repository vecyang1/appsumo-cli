# AppSumo Public Reviews API Discovery

Discovery date: 2026-08-14

## Conclusion

Product reviews are served by a public, unauthenticated JSON endpoint. No cookie,
token, or browser session is involved, and none must be sent.

```
GET https://appsumo.com/api/v2/deals/{deal_id}/reviews/
    ?from=0&items_per_page=100&sort=date&order=asc
```

Response envelope:

```json
{ "comments": [ { "id": 378596, "rating": 5, "title": "...", "comment": "...", "children": [...] } ],
  "meta": { "total": 224, "count": 100 } }
```

## For Agents

Use the CLI. It already encodes everything below.

```bash
appsumo reviews growify --json > growify-reviews.json
```

The JSON payload is `{product, fetch, warnings, reviews}`. Check `fetch.complete`
before analyzing:

- `true` — every review the API reports was collected.
- `false` — the crawl was short or capped; read `warnings`.
- `null` — the API returned no `meta.total`, so completeness is **unknown**. It is
  not a synonym for `false`.

Warnings are printed to stderr, so `--json` stays a clean pipe.

## Three Decoys

Each of these returns HTTP 200 with plausible-looking data and a wrong answer.

### 1. `page` is accepted and ignored

The API and the server-rendered page both accept `page` and neither reads it.
`from` is the only real offset.

```
?page=1&items_per_page=5&from=0  -> ids 378596, 377926, 376883, 376343, 376312
?page=2&items_per_page=5&from=0  -> ids 378596, 377926, 376883, 376343, 376312   (identical)
?page=1&items_per_page=5&from=5  -> ids 376082, 375906, ...                      (advanced)
```

A crawler walking `page=1..N` collects page one N times and reports `N x 5`
reviews. `FetchAllReviews` guards this: a window that yields no new ids stops the
crawl and emits a warning instead of looping to the request cap.

### 2. The reviews *page* cannot be paginated at all

`https://appsumo.com/products/<slug>/reviews/?page=12` renders the same five
reviews as page 1, in a real browser, at every page number — including page
numbers past the end. Its own pager links to `?page=N`.

The cause is in `__NEXT_DATA__`: the route `/products/[slug]/reviews/list/[[...params]]`
reports `"gsp": true`, so it is generated by `getStaticProps`. Query strings are
structurally invisible to `getStaticProps`, and the embedded payload is always
the same five-review seed with `meta: {"total": 224, "count": 5}`. Scraping that
HTML yields five reviews per product no matter how many pages are walked.

### 3. `/api/v2/deals/?slug=<slug>` ignores the slug

It returns 200 with a default deal list. Requesting `?slug=growify` returned
Vectera. It is not a slug resolver.

## Resolving a Slug to a Deal ID

The only published mapping is the `__NEXT_DATA__` island on the product's own
page: `props.pageProps.deal.id`. `ResolveProduct` reads it from
`/products/<slug>/reviews/` and also picks up `deal.deal_review`, which carries
the site's own rating distribution — useful as an independent completeness check.

A product can carry more than one deal id (Growify's review records report
`deal_id: 254412` while the page reports `257731`). Both ids return the same 224
reviews, so reviews are aggregated per product rather than per deal.

## Pagination Behaviour

| Request | `meta.count` | Returned |
|---|---|---|
| no params | 20 | default page size |
| `items_per_page=100&from=0` | 100 | 100 |
| `items_per_page=250&from=0` | 224 | all 224 — no observed clamp |
| `from=220&items_per_page=100` | 4 | tail |
| `from=224` | 0 | empty, terminates the walk |
| `from=500` | 0 | empty |

`sort` and `order` are honoured: `order=asc` flips to oldest-first, `sort=helpful`
reorders by votes, and an unrecognised `sort` falls back to the default rather
than erroring. The CLI passes both through without a local allowlist, because a
client-side vocabulary that disagrees with the server is worse than none.

The CLI defaults to `sort=date&order=asc`. Offset pagination over a live list is
only stable when new rows land at the end; under the site's default newest-first
order, a review posted mid-crawl shifts every later offset by one and one review
is silently skipped.

The walk ends on an empty window rather than on `collected >= meta.total`, so a
stale total cannot truncate the result.

## Review Record Fields

`id`, `deal_id`, `parent_id`, `level`, `title`, `comment`, `rating`, `created`,
`modified`, `up_votes`, `down_votes`, `would_recommend`, `incentivized`,
`purchased`, `approved`, `edited`, `status`, `display_path`, `pinned`,
`resolved`, `followup`, `video_file`, `video_thumbnail`, `search_after`,
`user` (`id`, `username`, `avatar`, `date_joined`, `deals_purchased`), and
`children` — nested replies, typically the founder's response.

`rating` is `null` on replies. `would_recommend` is frequently `null`. These are
decoded as pointers so an absent field stays unknown instead of collapsing to 0
or false.

## Verification

Both products were crawled live and reconciled against the rating distribution
published on the product page — a source independent of `meta.total`.

| Product | Reviews | Requests | Site distribution | Crawled distribution |
|---|---|---|---|---|
| `growify` | 224 / 224 | 4 | 1:12 2:2 3:4 4:10 5:196 | identical |
| `tidycal` | 917 / 917 | 11 | 1:46 2:42 3:84 4:116 5:629 | identical |

`tidycal` completed in ~11s. An unknown slug exits 1 with the resolved URL in the
message.

## Scope

Reviews are a public surface and are deliberately **not** added to
`docs/openapi/appsumo-account.openapi.yaml`, which is the session-gated buyer
account contract that the Printing Press baseline and `shipcheck` verify.

A sibling endpoint, `/api/v2/deals/{deal_id}/questions/`, carries the product Q&A
with the identical envelope and pagination contract. It is not wired into the CLI.
